# Redis 缓存层说明

## 1. 设计目标

缓存是数据库或外部服务的加速层，不是事实来源。通用层只保留两个不变量：

1. 选择受控的 Redis connection。
2. 生成隔离、可版本化且不泄漏业务标识的 key。

不在 `CacheScope` 重复实现 `get`、`put`、`remember` 等 Redis 已有命令，也不为每个业务创建 `BackstagelClientsCache`、`BackstagelSocketClientsCache` 等空壳类。业务直接使用 Redis 的 String、Hash、Set、ZSet、Pipeline、Lua 等原生能力。

## 2. 代码位置与职责

```
app/Caches/
├── CacheManager.php  # Redis Factory、默认 connection、根命名空间
└── CacheScope.php    # 当前作用域的 Redis connection 与 key 生成
```

- `CacheManager` 注入 `Illuminate\Contracts\Redis\Factory`，由 `AppServiceProvider` 完成绑定。
- `CacheScope` 只提供 `connection()` 与 `key()`；不包装任何 Redis 读写命令，不承载用户、订单、短信等业务规则。
- 数据库查询仍由 Repository 负责；缓存不是 Repository 的替代层。

## 3. 调用方式

业务 Service 注入 `CacheManager`，使用固定的、由代码控制的作用域：

```php
use App\Caches\CacheManager;

final class UserService
{
    public function __construct(
        private AdminUserRepository $users,
        private CacheManager $cache,
    ) {}

    public function cacheSnapshot(int $id, array $snapshot): void
    {
        $scope = $this->cache->scope('users');
        $key = $scope->key($id);

        $scope->connection()->setex(
            $key,
            300,
            json_encode($snapshot, JSON_THROW_ON_ERROR),
        );
    }
}
```

读取、Hash、集合和脚本都直接调用 Redis connection：

```php
$scope = $cache->scope('users');
$key = $scope->key($id);
$redis = $scope->connection();

$raw = $redis->get($key);
$redis->hGet($key, 'nickname');
$redis->sAdd($key, $member);
$redis->eval($script, [$key], 1);

// 选择非默认 Redis connection；连接名必须来自代码或受控配置。
$cache->scope('reports', 'default')->connection()->get($key);
```

Redis 未命中时的返回值、数组/对象的编码方式、事务和错误处理由具体业务协议决定。不要把请求参数直接传给 `scope()` 或 connection 名称。

## 4. Key 与安全边界

`key()` 生成的逻辑 key 结构为：

```
{namespace}:{version}:{scope}:{HMAC-SHA256(identifier)}
```

手机号、token、完整请求参数等标识不会原文写入 key。HMAC 密钥来自 `CACHE_HASH_KEY`，未设置时使用 `APP_KEY`；密钥轮换会让旧 key 自然 miss。摘要只保护 key 面的意外暴露，不是认证、授权或防枚举机制。

`namespace`、`version`、`scope` 会规范化为小写 ASCII，非法值直接抛 `InvalidArgumentException`。业务标识最长 256 字节且不能含控制字符。

`CacheScope` 生成的是逻辑 key。直接 Redis connection 的实际后端 key 还会受到 `config/database.php` 中 `REDIS_PREFIX` 的影响；`CACHE_PREFIX` 只作用于 Laravel Cache Store，不作用于这里的原生 Redis 命令。

## 5. TTL、数据与并发

- 本层不校验 TTL；业务必须选择合适的 Redis 原生命令。字符串值优先使用 `SET ... EX/PX` 或 `SETEX`，避免复刻 ebanos 的独立 `SET` 再 `EXPIRE`。
- Redis 不自动序列化 PHP 数组或对象。业务要么使用 String/Hash/Set 等合适的数据结构，要么显式 JSON 编解码并处理失败。
- Hash、Set、ZSet 等 key 的过期时间需显式设置；涉及“写入并设置 TTL”的强一致语义时使用 transaction、pipeline 或 Lua。
- 幂等占位、去重等使用原生 `SET NX EX`；一次性消费、分布式锁、限流等使用 Redis 原子命令、Lua 或 Laravel Lock/RateLimiter，不能把多条命令当成原子操作。
- 禁止 `flushdb`、`flushall` 和依据用户输入拼接 scope、connection 或 key。

## 6. 与 ebanos 的借鉴边界

可以借鉴：统一应用前缀、按业务域划分 key、按用途选择 Redis connection。

不直接复制：每个业务建立只定义常量的缓存类、Singleton 持有连接、固定的 `get/set/del` 转发层、分离 `SET`/`EXPIRE`、没有 TTL 的 Hash，以及 `exists` 后再写入的竞态流程。

因此业务命令保持 Redis 原样，通用层只处理 key 与 connection：

```php
$scope = $this->cache->scope('users');
$scope->connection()->setex($scope->key($userId), 300, $payload);
```

## 7. 配置与验证

`.env` 可配置：

- `CACHE_REDIS_CONNECTION`：`CacheManager` 默认 Redis connection，默认 `cache`。
- `CACHE_NAMESPACE`：应用/环境隔离前缀；未设置时默认 `pc-management-{安全化 APP_ENV}`。
- `CACHE_VERSION`：key 版本；升级后旧 key 自然失效。
- `CACHE_HASH_KEY`：HMAC 密钥；未设置时回退 `APP_KEY`。
- `REDIS_PREFIX`：直接 Redis connection 的底层前缀；与 `CACHE_PREFIX` 不是同一配置。

部署前必须先注入非空的 `APP_KEY` 或 `CACHE_HASH_KEY`，并确认默认 Redis connection 已在 `config/database.php` 中配置。

缓存层单元测试不连接外部 Redis，只验证 connection 选择、key 生成与输入边界：

```bash
docker compose -f docker-compose.image.yml exec -T app php artisan test --filter=CacheScopeTest --no-coverage
docker compose -f docker-compose.image.yml exec -T app vendor/bin/pint --test
```
